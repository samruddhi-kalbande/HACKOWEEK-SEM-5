API Endpoints Specification

Click an endpoint to load its configuration into the live interactive tester.

GET /api/students

List students with filtering by branch, year, status, min_cgpa, and full-text search.

GET /api/students/:id

Get specific student information by ID (e.g. STU001).

POST /api/students

Insert a new student into the Kaggle database collection.

PUT /api/students/:id

Update properties (e.g. CGPA, attendance, status) of an existing record.

DELETE /api/students/:id

Delete a student from the database by ID.

GET /api/stats

Get computed metrics, distributions, and top performer analytics.

GET /api/dataset-info

View dataset provenance, feature list, and multi-week roadmap.

📐 The 6 Guiding Architectural Constraints of REST

1. Client-Server Separation

User interface concerns are decoupled from data storage concerns, improving portability of user interfaces across mobile and web.

2. Statelessness

Each request from client to server contains all context needed to satisfy the request. No session state is retained on the server.

3. Cacheability

Responses must implicitly or explicitly define themselves as cacheable or non-cacheable to prevent clients from reusing stale data.

4. Uniform Interface

Standardized URIs for resources (e.g. /api/students) with standard HTTP verbs (GET, POST, PUT, DELETE).

5. Layered System

Client cannot ordinarily tell whether it is connected directly to the end server, or to an intermediary such as a proxy or load balancer.

6. Code on Demand (Optional)

Servers are able to temporarily extend or customize the functionality of a client by transferring executable code (e.g. JavaScript).

🎯 Frequently Asked Whiteboard Interview Challenges

Q1: PUT vs POST vs PATCH

POST creates a subordinate resource (ID generated by server).
PUT replaces the entire resource or creates it at a known URI.
PATCH applies partial modifications to a resource.

Q2: Idempotency in HTTP Methods

GET, PUT, DELETE, HEAD are idempotent (making identical requests multiple times produces the same system state). POST is non-idempotent.

Q3: Proper HTTP Status Code Usage

200 OK: Successful query/update.
201 Created: Successful creation via POST.
400 Bad Request: Malformed payload / missing field.
404 Not Found: Resource does not exist.
409 Conflict: Duplicate email or unique key.

Q4: How do you handle pagination at scale?

Using limit and page (or cursor-based pagination with last_seen_id) prevents loading millions of records into memory at once, reducing latency and DB load.
